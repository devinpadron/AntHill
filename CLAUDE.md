# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

AntHill is an Expo/React Native app (bare workflow, `expo run:*`) for small catering businesses to schedule staff onto events, track hours, and manage per-company checklists and forms. Backend is entirely Firebase (Auth, Firestore, Storage, Cloud Messaging) accessed through `@react-native-firebase/*` — there is no custom API server in this repo.

## Commands

```bash
npm start            # Expo dev server
npm run ios          # expo run:ios (native build; dev client, not Expo Go)
npm run android      # expo run:android
npm run lint         # prettier --check .
npm run format       # prettier --write .
node run [ios|android]  # nuke node_modules/package-lock/ios/android/.expo, npm install, expo prebuild, expo run
```

`node run` is the recovery path when native builds or pods go stale — it is destructive and rebuilds everything from scratch.

`npm test` maps to `jest`, but there is no jest config and `src/tests/Calendar.test.tsx` is empty — the test setup is not wired up. Don't assume tests run.

A husky pre-commit hook runs `prettier --write .` and `git add -A`. Prettier settings are non-default: **tabs, width 4, double quotes** (`.prettierrc.json`).

`android/` and `ios/` are gitignored and generated by `expo prebuild` — never edit native projects expecting the changes to persist.

## Environment

- `.env` (gitignored) supplies `GOOGLE_PLACES_API_KEY`, imported via `@env` (`react-native-dotenv`, configured in `babel.config.js`) and also exposed through `app.config.js` → `expo.extra`.
- `google-services.json` / `GoogleService-Info.plist` are gitignored; EAS builds supply them via `GOOGLE_SERVICES_JSON` / `GOOGLE_SERVICES_PLIST`.
- App version lives in `app.config.js` (`expo.version`) and must be bumped for releases — see the version gate below.

## Architecture

### Entry and provider chain

`index.js` registers the app (with a `HeadlessCheck` that bails when iOS launches in the background for a push) and installs the FCM background handler. `App.tsx` nests providers in an order that matters:

`GestureHandlerRootView → SafeAreaProvider → UploadManagerProvider → UserProvider → CompanyProvider → NavigationContainer → NotificationProvider → NotifierWrapper → AppNavigator`

`NotificationProvider` sits _inside_ `NavigationContainer` because push handling navigates. `CompanyInitializer` bridges the two data contexts: when `user.loggedInCompany` changes it calls `setActiveCompany`, which is what makes company data load.

### Dev vs prod database

`src/constants/firestore.js` exports the single shared `db`. **Under `__DEV__` it points at a separate Firestore database named `test`.** All services import this default export; never construct a Firestore instance elsewhere or dev writes will hit production.

### Firestore data model

Everything company-scoped hangs off `Companies/{companyId}`:

```
Users/{userId}                              # global profile: name, email, companies[], loggedInCompany, fcmToken[]
Users/{userId}/Preferences/settings         # per-user settings
AppData/Data.required_version               # minimum app version gate

Companies/{companyId}                       # name, accessCode
  Users/{userId}.role                       # membership + role (manager | user | owner) — Role enum in src/types/enums
  Settings/preferences                      # CompanyPreferences (feature flags + custom form schemas)
  Events/{eventId}
    Attachments/{id}
    Checklists/{checklistId}
  TimeEntries/{entryId}
    Attachments/{id}
  Packages/{packageId}
  Checklists/{checklistId}
  EventLabels/{labelId}
```

A user belongs to many companies (`companies[]`) and has one active one (`loggedInCompany`); role is per-company, so `isAdmin` must be re-derived whenever the active company changes.

### Layering

`screens/` and `components/` never touch Firestore directly. The chain is **screen → hook (`src/hooks`) → service (`src/services`) → `db`**. Services are thin, per-collection modules that take `companyId` as their first argument and expose both one-shot (`getX`) and realtime (`subscribeX`, returning the unsubscribe fn) variants. Keep new data access in this shape.

### Contexts

- `UserContext` — Firebase Auth state, the `Users/{uid}` snapshot, per-company `userPrivilege`/`isAdmin`, and user preferences, all via live subscriptions. Persists `AUTH_STATE` in AsyncStorage so a returning user sees the app shell immediately (`initializing` vs `isLoading` are distinct: `initializing` gates the splash screen, `isLoading` gates data). Unverified emails are signed out with a resend prompt.
- `CompanyContext` — active company doc plus `CompanyPreferences`, merged over `defaultPreferences` so missing keys never break the UI. Preference writes go through `updatePreferences` (merge-write to `Settings/preferences`).
- `UploadManagerContext` — centralized Firebase Storage uploads/deletes for attachments, keyed by parent type (`"Events" | "TimeEntries"`), with progress map, cancellation on unmount, and NetInfo awareness. Attachment work belongs here, not in screens.
- `NotificationContext` — FCM permissions, token save/refresh onto `Users/{uid}.fcmToken`, foreground in-app banners (`react-native-notifier`), and deep-link routing by `data.type` (`assignment`, `update`, `timesheet_approval[_batch]`, `new_user_joined`, `user_left`). It calls `swapUserCompany` before navigating, since a notification may target a company the user isn't currently in.

### Navigation

`AppNavigator` picks `AuthStack` or `HomeTabs` off `loggedIn`. Tabs are **feature-flagged by company preferences** — the Availability and Clock tabs only mount when `preferences.enableAvailability` / `enableTimeSheet` are set, so a screen's reachability depends on company config.

Push-driven navigation goes through `src/navigation/navigationRef.ts`: `pendingNavigation.setAction(routeName, params)` queues a route, and `App.tsx` polls `executeIfReady()` every 500ms for the first 5s (plus `NavigationContainer.onReady`) to cover notifications that arrive before the navigator mounts. Route params for these targets are typed in `RootStackParamList` — add new deep-link targets there.

### Company-customizable forms

`CompanyPreferences.eventForm` and `.timeEntryForm` are schemas (`{title, description, fields[], isEnabled}`) stored per company and rendered dynamically (`src/components/time/CustomFormRender.tsx`, admin editors under `src/screens/settings/admin/`). Event/time-entry fields are therefore not a fixed shape — treat submitted form values as company-defined data.

### Version gate

On launch `checkAppVersion()` compares `app.config.js` version against `AppData/Data.required_version` and shows a non-dismissible "Update Required" alert linking to the store. Bumping `required_version` in Firestore force-updates all clients.

## Conventions

- TypeScript is non-strict; a fair amount of Firestore data is typed `any`. Shared models live in `src/types` and are re-exported from `src/types/index.ts` — import from `"../types"`.
- Services log errors with `console.error` and either rethrow (mutations) or return a null/empty fallback (reads). Follow the existing choice per module rather than mixing.
- `src/constants/colors.ts` holds the palette; screens are grouped by feature under `src/screens/<feature>/` with matching `src/components/<feature>/`.
