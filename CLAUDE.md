# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

AntHill is a staffing app for small catering businesses: schedule staff onto events, track hours, run payroll review, and manage per-company checklists, packages and custom forms. Backend is entirely Firebase (Auth, Firestore, Storage, Cloud Messaging, Hosting) through `@react-native-firebase/*` — there is no custom API server here.

The repo holds **four** things:

| Path              | What                                                                                                            |
| ----------------- | --------------------------------------------------------------------------------------------------------------- |
| `src/`, `App.tsx` | The Expo/React Native app (bare workflow, `expo run:*`, dev client — not Expo Go)                               |
| `web/`            | The admin web portal — a Vite/React SPA that **compiles `src/services` verbatim** through a Firestore shim      |
| `tools/`          | Migration + operational scripts (`firebase-admin`) and security-rules tests, each with their own `package.json` |
| root config       | `firestore.rules`, `storage.rules`, indexes, deploy scripts, `firebase.json`                                    |

Cloud Functions live in a **separate repo** (`~/repos/AH_Functions`) — see `CLOUD_FUNCTIONS_HANDOFF.md`.

# Guards / tests

cd tools/rules-tests && npm test   # security rules, via firestore emulator

`npm test` maps to `jest` but there is **no jest config and no test files** — it does not run. The real gates are `npm run typecheck`, `tools/check-layering.sh`, and the two suites under `tools/`.

### Pre-commit hook

`.husky/pre-commit` runs, in order: `prettier --write .` → `git add -A` → `./tools/check-layering.sh` → `npm run typecheck` → (if `web/node_modules` exists) `npm --prefix web run typecheck` and `node scripts/check-icons.mjs`.

Prettier settings are non-default: **tabs, width 4, double quotes** (`.prettierrc.json`).

`android/` and `ios/` are gitignored and generated by `expo prebuild` — never edit native projects expecting changes to persist. `patches/` holds a `patch-package` patch applied via `postinstall`.

## Environment

- `.env` (gitignored) supplies `GOOGLE_PLACES_API_KEY`, imported via `@env` (`react-native-dotenv`, `babel.config.js`) and also exposed through `app.config.js` → `expo.extra`. `app.config.js` additionally reads `GOOGLE_MAPS_ANDROID_API_KEY` from `process.env` — without it, `react-native-maps` renders a blank grey tile on Android. Set it in `.env` and in the EAS environment.
- `google-services.json` / `GoogleService-Info.plist` are gitignored; EAS supplies them via `GOOGLE_SERVICES_JSON` / `GOOGLE_SERVICES_PLIST`.
- Portal env: `web/.env.local` (gitignored — Firebase web config, Maps key) and `web/.env.production` (committed — sets only `VITE_ANTHILL_DB=default`, the opt-in to production data). Anything other than `"default"` means the `test` database.
- App version lives in `app.config.js` (`expo.version`, currently **1.3.0**). EAS uses `appVersionSource: "remote"` with `autoIncrement` on production builds.

## Architecture

### Entry and provider chain

`package.json` `main` points at `node_modules/expo/AppEntry.js`, which imports **`App.tsx` directly — `index.js` is never evaluated**. Anything that must run at startup (the `kvStore` registration, the `locationTasks` side-effect import) lives at module scope in `App.tsx`.

```
GestureHandlerRootView → SafeAreaProvider → ThemeProvider → AppGate →
UploadManagerProvider → UserProvider (+ ThemeSync) → CompanyProvider →
NavigationContainer → NotificationProvider → NotifierWrapper →
CompanySwitcherProvider → AppNavigator
```

Order is load-bearing in three places:

- `ThemeProvider` is **above** everything so the splash and the gate screens are themed. It cannot read the user document itself; `ThemeSync` is the bridge that pushes the account's saved appearance down into it.
- `AppGate` wraps the whole tree, so a forced update / schema mismatch / maintenance freeze blocks rather than renders behind.
- `NotificationProvider` sits **inside** `NavigationContainer` because push handling navigates.

`CompanyProvider` needs no bridge component — it subscribes to `useUser().companyId` directly. (v1's `CompanyInitializer` is gone.)

`DIAGNOSTICS_MODE` in `src/constants/devFlags.ts` (`__DEV__ && false`) swaps in `DiagnosticsApp`: the real contexts against the `test` database with a route-name-identical navigator, deliberately omitting `AppGate` and `NotificationProvider`.

### Which database

`src/constants/database.ts` is the single source of truth: `DATABASE_ID` is `"test"` under `__DEV__`, `"(default)"` otherwise. `src/lib/db.ts` builds the one shared Firestore handle from it. **Never construct a Firestore instance anywhere else.**

`test` is a full copy of production, so nothing on screen distinguishes them — `DatabaseBadge` (dev-only) and `DATABASE_LABEL` exist for that. Every on-disk key namespace (SWR cache, upload queue, location session) is suffixed with `DATABASE_ID` so a dev queue can never drain into production.

### The launch gate

`useAppGate` (rendered by `src/components/ui/AppGate.tsx`) checks three signals, in priority order, on cold start **and on every return to foreground**:

1. `appConfig/schema.maintenance` — deliberate write freeze → `maintenance`
2. `AppData/Data.required_version` vs `expo.version` → `update`
3. `appConfig/schema.activeVersion` not in `SUPPORTED_SCHEMA_VERSIONS` → `schema`

`update` and `schema` are kept distinct on purpose: an update gate is fixed by installing a newer build; a schema gate is not fixed by anything the user can do, and after a rollback sending them to the App Store is actively wrong.

`src/constants/schema.ts`: this build ships `SUPPORTED_SCHEMA_VERSIONS = [2]` and `FALLBACK_ACTIVE_SCHEMA_VERSION = 2`. Every read in `appConfigService` **fails open** — an outage must never gate users out — and both reads go **cache-first with a background revalidate**, so raising `required_version` engages on the next foreground rather than the same launch.

### Firestore data model (v2 — flat, lowerCamel)

The v1 nested PascalCase schema (`Companies/{id}/Events/...`) is **gone from the app**. Collection names live in `src/constants/paths.ts` (`C`), which **only `src/services/**` may import**.

```
users/{userId}                      firstName,lastName,email,emailLower,phone,
                                    loggedInCompanyId, fcmTokens[], lastSeenAppVersion/At
userSettings/{userId}               preferredMapApp, defaultCalendarFilter, theme,
                                    locationConsentByCompany{companyId: Timestamp}
companies/{companyId}               name, accessCode, timeZone (IANA)
companyPreferences/{companyId}      feature flags, reminder schedules, location settings,
                                    eventFormSchemaId / timeEntryFormSchemaId
memberships/{companyId}_{userId}    role, status, denormalized name/email/phone,
                                    visibility, groupIds[], notifications?, joinedViaCode?
groups/{groupId}                    name, joinCode, joinVisibility
groupJoinCodes/{code}               doc id IS the code; `list` is denied so it cannot be enumerated
formSchemas/{schemaId}
events/{eventId}                    dateKey, isAllDay, startAt/endAt, durationSeconds,
                                    adminNotes/workerNotes, locations{}, assignedUserIds[],
                                    assignedCount, packageIds[], checklistIds[], labelId,
                                    audienceGroupIds[], audienceUserIds[], isTargeted,
                                    responseCounts{}
eventResponses/{eventId}_{userId}   status, respondedAt, acknowledgedAt, dateKey
eventChecklistStates/{eventId}      state{checklistId: {itemId: 0|1|2}}
timeEntries/{entryId}               status, clockInAt/clockOutAt, dateKey, workedSeconds,
                                    pausedSeconds, pauseStartedAt, formSchemaIds/Hashes,
                                    formResponses, submission, review, locationTracking, legacy
  connections/{eventId | custom_*}
  edits/{entryId}-{seq}
  locationSegments/{entryId}-{seq}
attachments/{attachmentId}          top-level, not per-parent
packages / checklists / eventLabels

AppData/Data.required_version       pre-auth, deliberately NOT renamed in v2
appConfig/schema                    pre-auth: activeVersion, maintenance, message
```

Conventions enforced across every document (`src/types/common.ts`):

- every instant is a `Timestamp` in a field ending **`At`**
- every calendar day is a `"YYYY-MM-DD"` string in a field ending **`Key`**
- every duration is whole seconds in a field ending **`Seconds`**
- every doc carries `id`, `createdAt`, `updatedAt`, `schemaVersion`; company-scoped docs carry `companyId`

`companyId` as a _field_ is what makes the flat layout safe: the rules read `resource.data.companyId`, and because Firestore rules are not filters, a query that does not carry `where("companyId","==",…)` is **rejected outright**.

Deterministic composite ids (`membershipId`, `eventResponseId`, `${entryId}-${seq}`) make re-running the migration idempotent.

A user belongs to many companies via `memberships`, and has one active one via `users.loggedInCompanyId`. Role is per-company, so `isAdmin` is re-derived from the membership subscription whenever the active company changes.

### Layering, and the guard that enforces it

**screen → hook (`src/hooks`) → service (`src/services`) → `src/lib/db`.** Services are thin per-collection modules taking `companyId` first and exposing one-shot (`getX`) and realtime (`subscribeX`, returning the unsubscribe synchronously) variants.

`tools/check-layering.sh` runs in pre-commit and enforces eight rules mechanically. Read it before restructuring anything — each rule exists because the corresponding bug shipped:

1. Nothing outside `src/services/**` may import `lib/db` or `@react-native-firebase/firestore`.
2. Services may not import from `contexts/`, `hooks/` or `screens/` — services are the bottom layer.
3. Any service file using `.where(` must have a `.limit(` somewhere in it. No unbounded queries.
4. No v1 field names (`clockInTime`, `assignedWorkers`, `workerStatus`, `editHistory`, `loggedInCompany`, `pauseStartTime`, `totalPausedSeconds`, `generalForm`, `eventForm`, …) read off document-shaped variables.
5. No `new Date(x.someAt)` on a Timestamp field — use `.toDate()`.
6. No `.exists` as a property. In RNFirebase v23 **`exists` is a method**, so `doc.exists` is always truthy. (`tools/migration` uses `firebase-admin`, where it really is a property, and is exempt.)
7. The same Firestore boundary applied to `web/src`, exempting `web/src/shim/**`, `web/src/contexts/UploadContext.tsx` and `web/src/lib/shimConformance.ts`.
8. No `@react-native-async-storage/async-storage` or `@react-native-community/netinfo` inside `src/services` — the portal compiles that tree and has neither. Use `src/lib/kvStore.ts` / `src/lib/connectivity.ts`, which live outside `services/` precisely so anything may import them.

The guard uses `find`, never `git grep`, so untracked new files are checked too.

### Contexts

- **`UserContext`** — auth, the `users/{uid}` snapshot, `userSettings`, and the active-company membership (role/`isAdmin`), all live. Session presence is decided **synchronously from the cached `authUser`**; `refreshVerification` is never awaited by the auth callback, so being offline cannot log anyone out. `src/lib/authSession.ts` persists the session with a 30-day offline grace window (`OFFLINE_GRACE_MS`, `src/constants/auth.ts`) — not a security boundary; rules still run server-side, and an authoritative rejection signs out immediately without waiting for grace. Re-checks fire on foreground and reconnect, debounced to 15 min. `initializing` gates the splash, `isLoading` gates data — they stay distinct. `logout` clears the FCM token, **clears all SWR caches** (shared phones), then signs out.
- **`CompanyContext`** — the company doc and `companyPreferences`, both live subscriptions merged over `defaultPreferences`. Also the source of `timeZone`. `updatePreferences` writes a **field-level patch**, never the whole object.
- **`UploadManagerContext`** — Firebase Storage uploads/deletes. Owns no Firestore access (metadata goes through `attachmentService`). Works offline: stage the file durably → write the attachment doc → enqueue the bytes → drain on reconnect.
- **`NotificationContext`** — FCM permission, token add/refresh onto `users/{uid}.fcmTokens`, themed foreground banners via `toast.info`, and deep-link routing. `screenName` from a push is **validated against a real route table**, never cast. Calls `setActiveCompany` before navigating, since a push may target another company.

### Theme / design system

`src/theme` replaced the old `src/constants/colors.ts` entirely.

- `palette.ts` — raw ramps, **the only file allowed to contain hex literals**. Private to `themes.ts`; screens never import it.
- `themes.ts` — semantic `ColorTokens` named for role (`surface`, `textSecondary`, `accentSubtle`), light and dark.
- `tokens.ts` — spacing, radius, type scale (with per-variant `maxFontSizeMultiplier`), elevation, motion, `hitTarget`, `hairlineWidth`, `iconSize`.
- `ThemeContext.tsx` — separates `mode` (`"light" | "dark" | "system"`, what the user asked for) from `scheme` (what renders). Persisted twice: AsyncStorage for a correct first frame, `userSettings.theme` for the durable per-account copy.
- `haptics.ts` — intent-named (`haptics.success()`, `.selection()`), fire-and-forget; the light tiers are iOS-only.

Import from `"../theme"`, never the individual modules. Screens are built from `src/components/ui` primitives (`Screen`, `ScreenHeader`, `Text`, `Button`, `Card`, `ListRow`, `Sheet`, `Icon`, `Toast`, …). A raw `TouchableOpacity`, a bare `<Text fontSize>`, or a hex literal in a screen means the thing you want belongs in `components/ui`.

The native launch screen is a **solid colour with no image** — `SplashScreen.tsx` draws the animated mark. The two colours in `app.config.js` duplicate `neutral[50]` / `dark.bg` and must be changed together.

### Navigation

`AppNavigator` → splash while `initializing` → `AuthStack` if not logged in → **`NoCompanyScreen` if signed in with no company** (gated on `!isLoading` so it doesn't flash on launch) → `HomeTabs`.

Tabs are feature-flagged off live company preferences: Availability needs `enableAvailability`, Clock needs `enableTimeSheet`. Because preferences are a live subscription, toggling a flag adds/removes a tab without a relaunch. Labels are hidden; badges come from `useEventPrompts` (unconfirmed shifts on Calendar, unanswered invitations on Availability) and share one style.

Stacks: `CalendarStack`, `AvailabilityStack`, `ClockStack`, `SettingStack` (which nests `PayrollReviewStack`), plus `AuthStack` and the dev-only `DiagnosticsNavigator`. Shared options in `stackOptions.ts`; screens draw their own headers.

Push-driven navigation goes through `src/navigation/navigationRef.ts`: `pendingNavigation.setAction(routeName, params)` queues a route; `App.tsx` polls `executeIfReady()` every 500 ms for 5 s alongside `NavigationContainer.onReady`. Deep-link targets are typed in `RootStackParamList` (`Details`, `TimeEntryDetails`, `EmployeeList`, `Availability`, `Clock`) and must also be added to the `ROUTES` allowlist in `NotificationContext`.

### Offline

The app is offline-first, and several rules follow from it. Read the header of `src/services/timeEntryService.ts` before touching any write path.

- **No transactions.** `tx.get()` bypasses the cache and fails outright offline. Compute from the snapshot the caller already holds, or use `FieldValue.increment` (a transform — it queues offline and the server applies it to whatever the doc holds).
- **Do not await mutations.** `set()`/`update()` promises resolve on _server_ acknowledgement, so awaiting hangs forever offline. Field mutations return once queued and hand the promise to `pendingWrites.track(label, promise)` so genuine rejections still surface.
- **Business timestamps are client-side** (`Timestamp.fromDate`). `serverTimestamp()` reads back as `null` in local snapshots, so a server-stamped pause is invisible to the device that made it. `createdAt`/`updatedAt` stay on `serverTimestamp` — nothing reads them.
- `src/types/sync.ts` — `SnapshotSync {fromCache, hasPendingWrites}`, passed as a **trailing** callback argument by services. `hasPendingWrites` needs `{ includeMetadataChanges: true }` on the subscription or it sticks true forever.
- `src/lib/connectivity.ts` — one shared NetInfo listener, `"unknown"` treated as online. A hint for _wording_ and retries only; never gate a write on it.
- `src/lib/kvStore.ts` — injected KV backend (AsyncStorage in `App.tsx`, localStorage in `web/src/main.tsx`). Throws if unregistered rather than silently no-opping.
- `src/services/offline/swrCache.ts` — deliberately narrow persisted SWR cache for reads that are _expensive to assemble even when local_ (currently only `useUserStats`). Do not reach for it for ordinary reads — Firestore's own disk cache already covers those. It revives `Timestamp` instances on read.
- Uploads: Storage has no offline queue, so `src/lib/uploadQueue.ts` (metadata, capped at 200, exponential backoff) + `src/lib/uploadStaging.ts` (bytes copied into `documentDirectory`, which the OS will not reclaim) are one.
- `useSyncStatus` + `OfflineBanner` are the single app-wide indicator. Per-screen offline UI is how you end up with five that disagree.

### Location tracking

Off by default per company, and everything about it is designed so the clock is never blocked.

- `src/lib/locationTasks.ts` defines `LOCATION_TASK` and `GEOFENCE_TASK` at **module scope**, imported for side effect from `App.tsx`. A task defined inside a component/effect does not exist when the OS wakes the bundle, and the event is dropped silently. Neither task may touch React, and **neither may clock anyone in or out** — the geofence only posts a reminder.
- `src/lib/locationSession.ts` is the on-disk contract between foreground and background (AsyncStorage directly, since a background wake may precede `registerKvStore`). `useLocationTracking` is the **only** writer of that mirror — a task using stale config means a missing write there.
- Points are batched into **segments** (`timeEntries/{id}/locationSegments/{entryId}-{seq}`), not one doc per fix. The summary on the parent entry carries a **status** (`recording | completed | declined | denied | unavailable`), so an absent track is never presented as a fact about the worker. `null` means the feature was never on for that entry.
- Consent is recorded per company in `userSettings.locationConsentByCompany` and mirrored locally so an offline clock-in can check it. `LocationConsentSheet` shows the Play-Store-required prominent disclosure; `allowDeclining` only controls whether it offers a real "no".
- Geofence reminders are posted on-device with **notifee** (not expo-notifications, which would fight RNFirebase for the FCM token) and carry the same `data` shape as server pushes so they route through the one table in `NotificationContext`.

### Company-customizable forms

`companyPreferences.eventFormSchemaId` / `.timeEntryFormSchemaId` are **references into `formSchemas`**, not inline schemas as in v1. Time entries store `formSchemaIds` plus `formSchemaHashes` so a schema mutated after publication is detectable. Rendered by `src/components/time/CustomFormRender.tsx`; edited under `src/screens/settings/admin/`. Treat submitted form values as company-defined data of no fixed shape.

Note the historical trap the layering guard now catches: the editor wrote `options` while the migration wrote `selectOptions`.

### Web portal (`web/`)

A Vite/React SPA at `hosting:portal` that **imports `src/services`, `src/hooks`, `src/types`, `src/constants`, `src/lib` and `src/utils` verbatim** through the `@app` alias. `@react-native-firebase/*` and a handful of native-only packages are aliased to adapters in `web/src/shim/` that re-expose the RNFirebase chaining API over the Firebase web SDK.

Rules for working in here:

- The alias list in `vite.config.ts` and the `paths` map in `web/tsconfig.json` **must stay identical**, or tsc type-checks the services against the real RNFirebase API the browser will never run.
- `resolve.dedupe` forces one React. Shared hooks resolve from the repo root's `node_modules` otherwise, giving two React copies and a null hook dispatcher.
- `__DEV__` is what selects the database (`VITE_ANTHILL_DB`), injected both by `define` (production build) and by a `transformIndexHtml` global (dev serve, where `define` skips modules outside the Vite root).
- **No predeploy hook in `firebase.json`, deliberately** — Firebase runs predeploy for channel deploys too, which once overwrote a staging build with a production one seconds before upload. Build and deploy are paired in `web/package.json` instead.
- Hosting header order matters: the catch-all comes first, `/assets/**` last, and the catch-all must carry `Cache-Control` because every route is served as `index.html` via the SPA rewrite.

### Security rules, indexes, deploys

`firestore.rules` contains **both** rulesets: the v1 (PascalCase) blocks, kept untouched so v1 remains the rollback target, and the v2 (flat) blocks below the banner at line ~161. v2 scoping is `resource.data.companyId` + `memberships/{companyId}_{userId}` with `status == "active"`.

- `./tools/deploy-firestore.sh` — `firebase deploy --only firestore:rules` **silently deploys nothing** with the array form of the `firestore` config in `firebase.json`, while still printing "Deploy complete!". The script deploys both databases and verifies two "released rules" lines.
- `./tools/deploy-indexes.sh` — the array form crashes the CLI on `indexes`, so the script swaps in a temporary single-object config. It can only target `(default)`; for `test`, run `cd tools/migration && node src/check-queries.mjs --db=test` and open the printed console URLs.
- `tools/rules-tests/` runs against the emulator with the Firebase web SDK, kept out of the app's dependency tree.
- `storage.rules` covers **three historical path layouts** — the current `companies/{companyId}/Events|TimeEntries/{parentId}/{fileId}` plus two legacy lowercase variants still referenced by live attachment records.

### Migration and ops tooling (`tools/migration`)

Its own `package.json` with `firebase-admin`, deliberately outside `src/` so admin SDK never enters the RN bundle. Scripts cover the v1→v2 migration (`migrate`, `verify`, `delta`, `golden`, `profile`), plus the cutover levers: `set-schema-version.mjs`, `set-required-version.mjs`, `set-maintenance.mjs`, `seed-app-config.mjs`, and `refresh-test.mjs`. It keeps its **own copy of the v1 collection names** — do not reuse `src/constants/paths.ts` for it.

### Cloud Functions

Not in this repo. `CLOUD_FUNCTIONS_HANDOFF.md` documents the v1→v2 trigger migration for `~/repos/AH_Functions`, the field-rename table, and two live hazards (two deployed functions with no source in that repo; deploying v2 triggers during a delta sweep would fire a real push per migrated document).

**Notification mutes are a second cross-repo contract.** `memberships/{id}.notifications` holds one boolean per channel (`src/types/identity.ts`), and `functions/src/utils/notifications.js` maps every push type onto a channel in `CHANNEL_BY_TYPE`, filtering in the one place every send passes through. Both sides **fail open** — absent means send, since the field is missing on every membership written before it existed. Adding a row to `NOTIFICATION_ROWS` without a matching entry in `CHANNEL_BY_TYPE` yields a switch that silences nothing. The manager-facing `team` switch was split into `teamMembers` / `availabilityConfirmed` / `availabilityDeclined`; `team` survives as a mirror (the OR of the three, written by `withLegacyTeamMirror`) so an un-deployed reader on either side under-mutes rather than over-mutes, and both repos expand a legacy `team: false` onto all three.

**The FCM payload contract is frozen**: `data.type`, `screenName`, `companyId`, `eventId`, `timesheetId` (comma-delimited for batch types), `userId`. Changing it here couples two deployments that are already hard to sequence. Types currently handled: `assignment`, `update`, `assignment_ack_nudge`, `availability_nudge`, `timesheet_approval[_batch]`, `timesheet_rejection[_batch]`, `new_user_joined`, `user_left`, and the on-device `clock_reminder`.

## Conventions

- TypeScript is **non-strict**, and a fair amount of Firestore data is typed `any` — which is exactly why `check-layering.sh` rules 4–6 exist as greps. Shared models live in `src/types` and re-export from `src/types/index.ts`; import from `"../types"`.
- Services log with `console.error` and either rethrow (mutations) or return a null/empty fallback (reads). Follow the existing choice per module.
- Screens grouped by feature under `src/screens/<feature>/` with matching `src/components/<feature>/`. StyleSheets are co-located as `Component.styles.ts`.
- Every list query needs an explicit `.limit()`, and the cap should be an exported constant when the caller can meaningfully hit it (see `EVENT_QUERY_LIMIT`).
- Comments in this codebase carry the _why_, usually the bug that motivated the shape. When changing such code, update the comment rather than deleting it.
